# Spec: Dual extraction for case ingestion

## Goal

Replace per-case human promotion review with a comparison-driven workflow: two
independent LLM extractions of the same source document are diffed; a human
reviews only the fields where the two disagree. Fields that both extractions agree
on can be treated as high-confidence without human review of the full record.

This reduces the human bottleneck from "read every field of every case" to "resolve
conflicts and spot-check a sample." At scale (hundreds to thousands of cases) it
is the only model that remains feasible.

Out of scope:
- Changing the quote-grounding gate (`check_source_integrity.py`) — that already
  runs and catches fabricated quotes; this spec sits on top of it.
- Automated YAML promotion without human sign-off — a human still approves the
  final merge, but from a much smaller conflict surface.
- Changing the existing `ingest_case.py` single-extraction path — dual extraction
  is a new flag/mode, not a replacement, so existing single-pass runs still work.

## Approach

### Why two cold extractions rather than one extraction + LLM review

An LLM reviewing another LLM's output is circular: the reviewer is influenced by
the first agent's confident framing, and both may share the same model biases.
True independence requires the second agent to read the source document with no
knowledge of what the first agent produced. The comparison step is then structural
— field A says X, field B says Y — not interpretive.

### Extraction independence constraints

- Extraction B is a fresh API call with an identical system prompt and the same
  source text, but no access to Draft A's output.
- Different temperature / sampling seed is sufficient to produce variation; using
  a different model is optional and adds complexity without guaranteed improvement
  in catching the class of errors we care about (misclassification, missed markets,
  wrong definition_status).
- The source text feed (PDF page cache) is shared — re-fetching the PDF is waste.

### Comparison (diff) step

A third agent (or a deterministic diff) compares Draft A and Draft B field by
field and produces a `ConflictReport`:

```
conflict_report:
  case_id: eu_sika_mbcc_2023
  agreed_fields: [...]
  conflicts:
    - field: product_markets[0].definition_status
      draft_a: defined
      draft_b: discussed
      source_excerpt: "the Commission considers..."
      resolution: null   # filled by human
    - field: product_markets[2].market_name
      draft_a: "Ready-mix concrete — Germany"
      draft_b: "Ready-mix concrete — DE"
      source_excerpt: null
      resolution: null
```

The comparison for qualitative fields (market names, definition_status,
theory_of_harm labels) is done by the third agent reading both drafts and the
source excerpt — not a string equality check, because equivalent-but-differently-phrased
values should not generate a false conflict. For numeric fields (deal value, shares,
page numbers) a simple equality check suffices.

**The third agent is the only one that reads Draft A before producing output.**
Its job is comparison, not extraction — it cannot introduce new hallucinations
about what the source says, only flag where A and B diverge.

### Human review surface

A human sees the `ConflictReport`, not the full YAML. For each conflict:
- the source excerpt is shown
- Draft A and Draft B values are shown side by side
- the human picks one, edits, or leaves a note

The merged YAML then goes through the existing promotion gates unchanged
(`check_source_integrity.py`, `validate_cases.py`, `promote_case_pipeline.py`).

### When to skip dual extraction

- Cases with a very small source document (< 10 pages): single extraction +
  human review of the full record is faster.
- Re-runs of cases already in `data/cases/` where only a specific focus
  (e.g. `theories_of_harm`) is being added: diff against the existing canonical
  record rather than running a full second extraction.

## Files

| File | Change |
|------|--------|
| `apps/api/scripts/cases/extract/ingest_case.py` | Add `--dual-extract` flag; when set, runs extraction twice and writes both drafts |
| `apps/api/scripts/cases/extract/compare_extractions.py` | New — LLM-assisted diff of two draft YAMLs; produces `ConflictReport` YAML |
| `apps/api/scripts/cases/promote/promote_case_pipeline.py` | Add optional `--conflict-report` flag; when present, require human resolution before promotion |
| `data/drafts/<jurisdiction>/<case_id>.draft_a.yaml` | Draft A output (dual-extract mode) |
| `data/drafts/<jurisdiction>/<case_id>.draft_b.yaml` | Draft B output (dual-extract mode) |
| `data/drafts/<jurisdiction>/<case_id>.conflicts.yaml` | ConflictReport (generated by compare_extractions.py) |
| `apps/api/tests/test_compare_extractions.py` | New — unit tests for conflict detection; fixture pair of diverging drafts |

## Verification

```bash
# 1. Run dual extraction on a known case
.venv/bin/python scripts/cases/extract/ingest_case.py \
  --case-id eu_sika_mbcc_2023 \
  --focus market_definition \
  --dual-extract \
  --max-cost 2.00

# 2. Confirm both drafts written
ls data/drafts/eu/eu_sika_mbcc_2023.draft_{a,b}.yaml

# 3. Run comparison
.venv/bin/python scripts/cases/extract/compare_extractions.py \
  --case-id eu_sika_mbcc_2023 \
  --draft-a data/drafts/eu/eu_sika_mbcc_2023.draft_a.yaml \
  --draft-b data/drafts/eu/eu_sika_mbcc_2023.draft_b.yaml

# 4. Inspect conflict report
cat data/drafts/eu/eu_sika_mbcc_2023.conflicts.yaml

# 5. Existing tests still pass
.venv/bin/python -m pytest tests/ -v -k "not indexed_cases and not ingest_case"
```

Expected: the conflict report for `eu_sika_mbcc_2023` (a well-covered case with a
verified canonical) should show zero or very few conflicts, validating that two cold
extractions converge on a known-good record.

## Cost note

Dual extraction approximately doubles the LLM extraction cost (the PDF fetch and
text extraction are shared). At ~$0.50–1.00 per extraction, each case costs ~$1–2
total. The human time saved on full-record review at scale far exceeds the API cost
at any plausible volume (the break-even is approximately 5 minutes of lawyer
attention per case avoided).

## Rollback

`--dual-extract` is an additive flag; removing it reverts to the existing single-
extraction path. No schema changes to `data/cases/` or `data/drafts/` are required
— draft_a and draft_b files are intermediate artifacts that can be deleted.
